# 0.9.0

Released 2026-10-11. The compiler and every library move to 0.9.0 together. An
entity can say the workflow it moves by, and whoever works a stage takes what's in
it for a while, so two never work the same thing at once.

## Workflows, with claims that run out

- **`define workflow order by stage { worked by worked_by  steps step }`** says the
  rules an entity moves by: the field it moves along, pointing at its stages; the
  stage's field listing the roles that work it; and the entity of steps from one
  stage to another, for the roles they list.
- **Claims are leases.** The workflow adds `held_by` and `held_until`, and the
  commands `claim`, `renew`, `release` and `move`. A claim lasts 10 minutes, or what
  `lease 30 minutes` says, unless it's renewed, so a worker that stops, like a
  laptop gone to sleep, lets go by itself. Nobody else moves what someone holds,
  and moving it on ends the claim.
- **A queue per role**, `order_work`, is a view the workflow adds: what's in the
  stages the role works, with who holds it until when. A worker listens to it and
  takes what's free.
- It's all said in the language a project could write by hand, and the
  [reference](/language/reference#define-workflow) shows it.

```one
define workflow order by stage {
	worked by worked_by
	steps step
	lease 30 minutes
}
```

## Times counted from now, anywhere

- **`10 minutes from now`** and **`2 days ago`** go anywhere a value does, not only in
  a filter, in minutes, hours, days or weeks. A command counts them from when it
  runs: `held_until = 30 minutes from now`, `require due > 2 days ago`.
- **Dates compare** with `<`, `>`, `<=` and `>=` in a command, like `held_until < now`.
- **A moment today** is shown as its time, like 7:25 PM; another day's, as its date.
